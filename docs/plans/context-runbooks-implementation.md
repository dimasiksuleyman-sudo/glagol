# План: постоянный контекст и ранбуки Глагола

Дата: 2026-09-13. План принят пользователем ответом «го».
Фактические статусы и проверки: [серия context-system](../workstreams/context-system/README.md).

Основание: потеря контекста чата и изучение локального
`C:/Projects/loyaltyboss-monorepo`. Первоначальный запрос — анализ и план;
затем пользователь разрешил реализацию. Commit, push, установка приложения
и публикация не входят в эту серию.

## 1. Задача и критерий результата

Новая сессия должна восстановить актуальную задачу, принятые решения,
проверенный результат и следующий шаг по короткому маршруту документов.
История нужна для подробностей, но не должна перечитываться целиком при старте.
Потеря контекста между этапами не должна превращать предположение в факт.

Система считается внедрённой, когда:

- Codex и Claude получают один порядок чтения через свои входные документы;
- есть одна выбранная серия работ и один следующий шаг внутри активной серии;
- отдельно записаны исходники, сборка, установка и публикация;
- каждый завершённый шаг имеет проверку, окружение и ограничение результата;
- незавершённый шаг можно продолжить после обрыва, сверив документы с Git;
- локальный гейт ловит ошибки структуры, ссылок и версий, включая отрицательные
  примеры, и работает без моделей, сети и сборки приложения;
- старые журналы сохранены как история, без ретроспективного изменения результатов.

### Что нельзя копировать буквально

1. **Только SHA из main.** В Глаголе работа после 0.2.1 намеренно хранится
   локально. Ссылка на такой commit допустима, но её область должна быть явно
   указана: локальная история, main или проверенный релиз.
2. **SHA через регулярное выражение по всей прозе.** В документах Silero есть
   хеши артефактов и лицензий. Проверять как Git-ссылки только специальные поля.
3. **NEXT = ARCHIVED.** Завершённой серии не нужен фиктивный следующий шаг:
   использовать `status: done`, `next: null`.
4. **Обязательный push для занятия шага.** Для текущего локального режима
   достаточно записи владельца и ветки; это не распределённая блокировка.
   Совместную работу через Git вводить отдельно, если она понадобится.
5. **Обнаружение только по наличию YAML-блока.** Ошибка формата не должна молча
   исключать серию из проверки. Каждый обычный подкаталог каталога серий обязан
   иметь валидный файл состояния; шаблоны хранятся отдельно.
6. **Проверка всех исторических путей на существование сейчас.** Удаление или
   переименование модуля не делает старый журнал ложным. Проверять актуальные
   структурированные ссылки, не все упоминания в истории.
7. **Масштаб монорепозитория.** Не переносить Supabase/Vercel-проверки, сайт
   документации, четыре продуктовых слоя, большой генерируемый индекс находок.
8. **Остановка после каждого микрошагa.** Контрольные точки нужны для сохранения
   результата; они не требуют повторного разрешения на уже согласованную работу.

Замечания по реализации образца: `runbook-check.mjs` читает
`apps/web/package.json`, требует одну строку NEXT даже в архиве и проверяет
commit subjects через `git log --all`, а SHA — относительно main. Появление
строки `PASS` и наличие commit сами по себе не доказывают, что тест запускался.

## 4. Предлагаемая структура и единственные источники данных

```text
AGENTS.md                              порядок работы и восстановления
CLAUDE.md                              архитектура; ссылка на общий порядок
docs/STATUS.md                         короткий генерируемый обзор
docs/context/project.json              общие факты и выбранная серия
docs/context/README.md                 формат, обновление, границы проверок
docs/workstreams/<id>/state.json        шаги, статусы, NEXT, владелец
docs/workstreams/<id>/README.md         цель, решения, scope, критерии
docs/workstreams/<id>/log.md            последовательный журнал результатов
docs/runbooks/README.md                 навигация по процедурам
docs/runbooks/windows-build.md          сборка и проверка артефакта
docs/runbooks/tts-smoke.md               Silero: программная и ручная QA
docs/runbooks/dictation-smoke.md         GigaAM, сервер, облако, микрофон
docs/runbooks/release.md                версия → сборка → QA → публикация
docs/findings/README.md                 открытые находки и ограничения
docs/templates/workstream/              образцы state, README, записи журнала
scripts/runbook-check.mjs               read-only проверка согласованности
scripts/context-status.mjs              write/check для docs/STATUS.md
scripts/runbook-check.test.mjs          проверки самого гейта
```

JSON выбран для небольших машинных данных: строгий разбор встроенным Node,
без YAML-зависимости и самодельного распознавания произвольного Markdown.
Описание решения и выводы проверок остаются обычным Markdown.

`project.json` содержит `schema_version`, `active_workstream`, дату наблюдения,
ссылки на текущие инструкции, сведения о сборке/установке/публикации с источником.
Версию исходников обзор читает из package.json через существующую проверку
версий; не хранить её второй независимой константой.

`state.json` содержит `id`, `status`, `next`, `steps`, `claim` и ссылки на
доказательства. Шаг: уникальный ID, название, статус и требуемая validation.
Статусы шагов: `pending`, `in_progress`, `blocked`, `done`, `cancelled`.
В активной серии `next` указывает на один незавершённый шаг; во время выполнения
остаётся на нём. Не более одного `in_progress`. У завершённой/отменённой серии
`next: null`; у приостановленной — явная причина и точка продолжения.
Зависимости, если нужны, задаются ID шагов; нельзя начать шаг до их завершения.

`claim`: идентификатор сессии/исполнителя, UTC-время и ветка; заполняется перед
техническим изменением. Старый claim требует сверки Git и причины передачи,
не снимается автоматически по таймеру. Пользователь может явно сменить задачу;
тогда прежняя серия получает checkpoint и состояние паузы.

В README серии не вести вторую ручную таблицу статусов. `docs/STATUS.md`
генерируется из этих данных и помечается как производный файл. Обзор показывает
выбранную серию, текущий шаг, последний подтверждённый результат, блокеры и
состояние доставки. Полная история остаётся в журналах.

## 5. Рабочий цикл

**Старт или восстановление:** прочитать AGENTS → STATUS → состояние и README
выбранной серии → последние относящиеся записи журнала → нужный runtime/runbook.
Затем `git status`, `git log`, при изменённом дереве `git diff` и staged diff.
Незнакомые изменения не приписывать себе и не перезаписывать. Противоречие
документа и кода сначала разрешать проверкой, затем добавлять исправляющую запись.

**Во время работы:** записать claim; выполнять согласованный шаг; сохранять
checkpoint после существенного решения, проверки, блокера и перед сменой задачи.
Checkpoint сообщает, что уже изменено, что проверено, что ещё не завершено и
каким действием продолжать. Не откладывать всё до финального ответа.

**Закрытие шага:** validation → запись результата → обновление состояния и NEXT
→ очистка claim → генерация STATUS → runbook:check. Не помечать шаг done, если
обязательная проверка не выполнена. Статусы отдельных проверок:
`PASS`, `FAIL`, `NOT_RUN`, `BLOCKED`, с объяснением последних двух.

Запись результата: задача и решение; изменённые файлы; точная команда и cwd;
дата; ОС/архитектура; относящиеся версии Node/pnpm/Rust/Python; код возврата и
решающая строка; ограничения; ссылки на артефакт/commit; следующий шаг.
Не требовать версии Python для docs-only проверки или Rust для изменения текста.
Логи не содержат пользовательскую речь, тексты документов или секреты.

Проверку привязывать к проверенному commit/дереву, отмечая незакоммиченные
изменения. Не требовать SHA будущего commit в файле, который войдёт в него:
до commit достаточно baseline и списка изменений; ссылку добавлять позже
отдельной записью. Не создавать цикл бесконечных «обновлений собственного SHA».

Новая находка: стабильный ID `GL-001`, наблюдение, известная причина или
`unknown`, модуль, затронутые сценарии, evidence, решение и критерий закрытия.
Состояния: open / planned / resolved / accepted. Принятое ограничение требует
причины; исправленная находка — результата проверки. Непроверенный сценарий QA
обозначать как пробел проверки, не как доказанную поломку.

## 6. Что проверяет автоматический гейт

- JSON/schema version, обязательные поля, уникальность ID, допустимые статусы.
- Наличие каждой серии в выбранном каталоге; повреждённый state — ошибка.
- Существование выбранной серии, согласованность NEXT/claim/статусов/зависимостей.
- У done-шага есть ссылки на обязательные проверки с успешным результатом;
  непроведённая ручная QA не превращается в PASS общей серии.
- Текущие внутренние ссылки разрешаются внутри репозитория; историческую прозу
  и локальные пути к старым артефактам целиком не сканировать.
- `docs/STATUS.md` совпадает с воспроизводимой генерацией. Генерация не включает
  текущее время запуска и имя текущей checkout-ветки; использует записанные факты.
- Согласованность четырёх источников версии через `check-version.mjs`.
- Только явно объявленные Git-ссылки: commit существует; `local` достижим из
  проверяемого HEAD; `main` — из доступного ref main с указанием его имени;
  релизная ссылка — из заявленного тега. Subject — описание, не уникальный ключ.
- После squash исторический local SHA не обязан быть предком нового main:
  добавить явное соответствие старой ссылки новому commit с evidence или
  статус `historical_unresolved`. Такой статус не считается доказательством
  актуального done-шага и не переписывает старый журнал.
- Отсутствующая история не означает «всё проверено»: локально итог INCOMPLETE,
  отдельный ненулевой exit code; CI загружает полную историю и требует полноты.

Гейт не делает fetch, не устанавливает зависимости, не запускает модель,
не проверяет пользовательскую БД и не публикует документы. Установка приложения
и GitHub Releases — внешние наблюдения с датой и источником, не вывод из Git.
Проверка доступности/хеша локального установщика — отдельная явная команда;
его отсутствие на CI нормально. Проза и реальность ручной QA остаются предметом
проверки исполнителем: структура evidence не является доказательством сама по себе.

## 7. Этапы внедрения

| Шаг | Работа и файлы | Критерий завершения |
|---|---|---|
| R1 | Создать AGENTS, docs/context/README; привести рабочие разделы CLAUDE к одному порядку, поправить ссылки PROJECT_STRUCTURE | Нет противоречий о порядке работы; документированы только существующие команды; исторические соглашения явно отделены |
| R2 | Добавить project.json, шаблон, серию context-system, генератор STATUS | Из короткого обзора восстанавливаются задача и NEXT; генерация детерминирована; текущие факты снабжены источниками |
| R3 | Реализовать runbook-check и тесты на временных Git-репозиториях; добавить scripts в package.json | Валидные данные проходят; каждый испорченный пример даёт ожидаемый ненулевой код; рабочие файлы тестами не портятся |
| R4 | Написать четыре практических ранбука, создать findings и серию проверки 0.4.0 | Шаги воспроизводимы по текущим исходникам; программная QA, ручная QA и доставка разделены; исторические результаты помечены как исторические |
| R5 | Подключить лёгкую проверку к .github/workflows/ci.yml, включить полную историю для проверки Git-ссылок | Проверка не требует скачивания моделей/NSIS; существующие Rust/TS/build gates сохранены; CI-конфигурация проверена локально |
| R6 | Провести контрольное восстановление по документам и закрыть context-system | Краткий отчёт без опоры на память чата правильно называет задачу, ветку, проверки, ограничения и NEXT; гейт проходит |

Порядок R1 → R2 → R3 → R4 → R5 → R6. Проектная серия context-system появляется
в R2; сведения о R1 заносятся со ссылкой на фактически выполненное изменение.
После её закрытия выбранной становится серия верификации 0.4.0. Это очередь
работ, а не разрешение устанавливать приложение или публиковать релиз.

Для R1 разрешить исторические противоречия CLAUDE следующим образом: единый
процесс держать в AGENTS, архитектуру в CLAUDE; старые sprint-правила вынести
в явно историческую справку с указанием происхождения. Сохранить ограничения
безопасности, независимость STT/TTS, paired RU/EN docs и проверку версий.
Текущий режим — локальная работа; не вводить автоматический push/merge.

### Проверки R3

Через встроенный `node:test`, без нового test framework:

- битый/отсутствующий state, неизвестная версия схемы, дубли ID;
- два выполняемых шага, NEXT отсутствует или указывает на done/чужой ID;
- done с обязательной NOT_RUN-проверкой, неправильно заполненный claim;
- завершённая серия с next=null проходит без фиктивного ARCHIVED-шага;
- повреждённая ссылка и изменённый вручную STATUS;
- несовпадение версий;
- выдуманный Git SHA, local commit вне main как положительный пример,
  тот же commit с ложной областью main как отрицательный;
- SHA-256 модели и UUID в прозе не воспринимаются как Git-ссылки;
- shallow clone/недостающий ref даёт INCOMPLETE, не ложный PASS;
- CRLF, кириллица и путь с пробелами;
- два запуска генератора дают одинаковый файл.

Новые команды: `pnpm runbook:check`, `pnpm runbook:test`,
`pnpm context:refresh`; запасной прямой вызов через Node документируется.
`runbook:check` включает проверку STATUS без его изменения.
Для этой работы не добавлять ESLint/Vitest и не обновлять pnpm/Rust: это
отдельные задачи. Docs-only шаги не требуют повторной сборки всей программы.

Внести в состояние и очередь на основании существующих журналов:

- исправление сигнала готовности микрофона и подтверждение пользователя;

- выбранную иконку и локальные сборки 0.3.0;
- интеграцию Silero и локальную сборку 0.4.0;
- неисполненную ручную QA установки/обновления, согласия, голосов и диктовки;
- непроверенную доступность официального endpoint модели в сети пользователя;
- известные локальные обходы pnpm и Pdfium как воспроизводимые ограничения;
- Yandex SpeechKit как будущий отдельный объём, не часть закрытия Silero.

Не переносить весь старый архив в новый формат. Новая серия ссылается на
`docs/day-logs/` и план Silero; результаты старых сессий не объявляются заново
выполненными. При обнаружении ошибки в старом журнале добавлять датированное
уточнение в новом, не исправлять прошлое незаметно.

За рамками внедрения: изменение TTS/STT, установка и обновление приложения,
публикация 0.4.0, SpeechKit, обновление зависимостей, автоматизация всех UI-тестов,
внешняя база знаний/плагин, распределённая блокировка нескольких агентов.

## 9. Приёмка без старого чата

После R6 исполнитель должен по файлам и Git ответить:

1. Что является текущей задачей и какой ровно один шаг следующий?
2. Где лежит решение о независимости диктовки и Silero?
3. Какие изменения после 0.2.1 есть локально и что известно об их публикации?
4. Какие проверки 0.4.0 выполнены, кем/когда, а какие остались ручными?
5. Как продолжить прерванный шаг и какие изменения в дереве уже существуют?

Ответы сверяются с реальными файлами и доказательствами. Имитация восстановления
не выдаётся за запуск отдельного нового чата. Если независимой сессии нет,
указать это в результате и проверить маршрут чтения в текущей сессии.

Ожидаемый объём: шесть конечных шагов, без новых production-зависимостей.
Последовательность выше — исходный план; фактическое выполнение отмечается
в state.json и журнале серии, а не определяется формулировками этого документа.

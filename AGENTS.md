# Работа с Глаголом

## Вход и восстановление

1. Прочитать [текущее состояние](docs/STATUS.md).
2. Прочитать `state.json`, README и последние записи журнала выбранной серии
   `docs/workstreams/`. Формат описан в [docs/context/README.md](docs/context/README.md).
3. Прочитать [CLAUDE.md](CLAUDE.md), [карту кода](PROJECT_STRUCTURE.md) и
   [ранбук](docs/runbooks/README.md) изменяемой подсистемы.
4. Сверить `git status --short --branch`, `git log -5 --oneline`,
   `git diff` и `git diff --cached`. Незнакомые изменения не перезаписывать.

После обрыва или свёртки контекста повторить сверку. Различать «сделал сейчас»
и «так записано в старом журнале». При расхождении сначала проверить факт;
не дописывать правдоподобные детали по памяти.

## Выполнение

- Работать в согласованном объёме. Не добавлять несвязанные исправления,
  обновления зависимостей или форматирование.
- Перед техническим изменением занять текущий шаг в state.json: `in_progress`,
  `claim` с владельцем, UTC-временем и веткой. Claim локальный, не распределённый
  замок. Чужой/старый claim сначала сверить с Git; передачу объяснить в журнале.
- После существенного решения, проверки или блокера писать checkpoint:
  что изменено, что проверено, что осталось, как продолжить.
- Завершать шаг после обязательных проверок. Записывать фактическую команду,
  окружение, код возврата, решающую строку и границы результата. Ручную проверку
  обозначать manual. NOT_RUN/BLOCKED/FAIL не равны PASS.
- Затем обновить статус/NEXT, очистить claim, выполнить `pnpm context:refresh`
  и `pnpm runbook:check`. При закрытии серии выбрать следующую или явно оставить
  проект без активной серии. Смена задачи пользователем сохраняет прежний checkpoint.
- Checkpoint не требует повторного разрешения на уже согласованную работу.
  Сторонние находки записывать в [реестр](docs/findings/README.md) отдельно.

## Доказательства и история

- Состояние серии — в state.json; STATUS генерируется, руками не редактируется.
- Журналы append-only. Исправление старой записи оформлять новой датированной
  записью, с указанием причины. Архив не является текущей инструкцией.
- Git SHA указывать в структурированных полях с областью local/main/release.
  Не путать код на ветке с опубликованным релизом. После squash сохранять
  объяснение соответствия старого и нового commit.
- Сборка EXE, установка на компьютер и публикация — разные наблюдения с датой
  и источником. Недоступность внешней проверки обозначать явно.
- Не записывать речь, документы пользователя, ключи или токены в evidence.

## Проверки и доставка

Контекст/ранбуки: `pnpm runbook:test`, `pnpm runbook:check` (прямые Node-команды
в документации). Для документации не пересобирать приложение без причины.
Изменения Rust: fmt, clippy, cargo test; TS: `pnpm exec tsc --noEmit`, build;
упаковка: NSIS build. Точные команды — в ранбуке Windows. ESLint/Vitest пока
не настроены; не заявлять об их запуске. Новые гейты проверять на испорченных
входах с ненулевым кодом возврата. Не ослаблять проверки ради зелёного результата.

Изменения поведения документировать в обеих USER_GUIDE и обеих частях README;
добавлять CHANGELOG. Внутренний процесс не требует изменений пользовательских
руководств. Источники версии синхронизировать через check-version.mjs.

Текущий режим — локальная работа. Commit, push, PR, merge, установка и релиз
выполняются в рамках явно согласованного задания; сам ранбук не даёт разрешения
на публикацию. Не менять глобальные настройки Git или инструментов ради гейта.
Conventional Commits, одна причина изменения на commit. Отчёт: результат,
проверки, ограничения, следующий шаг; не требовать длинного шаблона для мелких правок.

Безопасность и архитектура — в CLAUDE.md и SECURITY.md. Этот файл является
единственным текущим описанием рабочего процесса для Codex и Claude.
